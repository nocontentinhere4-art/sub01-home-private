## Kimi's answer (verbatim)

## Verdict

**Hold the commit.** I found one definite blocking teardown/privacy bug, and one source-gate mismatch that is blocking unless `vagon.connected` is already phase-qualified. The normal running epoch/upload path is otherwise careful: I do not see a Ready-pointer race or an epoch mistake that lets a rejected frame be uploaded.

### 1. BLOCKING: `EndPlay` closes the gate but leaves the feed bound in the MID

`EndPlay` does this:

```cpp
FeedFrame=nullptr;
PublicConfirmedAt=-1;
FeedSourceConnected=false;
```

but does not call `SelectMonitorFrame()` or otherwise change `PCFrame`. Consequently:

- `BoundFrame` can still reference the feed texture.
- `MonitorMaterial` can still have `PCFrame == feed texture`.
- The timer is then cleared, so there need not be another selection that repairs it.
- `BoundFrame` also keeps the texture referenced.

Clearing the conditions used by future gate decisions does not undo the previous material write.

After clearing the feed state, force a fallback selection, for example:

```cpp
ShowFrame(TerminalCanvas); // sets OwnFrame and reselects away from the feed
```

For robust teardown, also clear `OwnFrame`/`BoundFrame` after the material has been reset, and handle a null `TerminalCanvas` by explicitly clearing the texture parameter.

A test must start with `BoundFrame == FeedFrame`, call `EndPlay`, and inspect the **actual material parameter**, not merely `IsMonitorFeedAllowed()`.

### 2. BLOCKING unless already implied by the backend schema: the Vagon predicate is weaker than the sidecar's

The merged sidecar requires, according to your description:

```text
vagon.connected AND phase == connected
```

`NoteMonitorFeedSource` checks only:

```cpp
(*Vagon)->TryGetBoolField(TEXT("connected"),Connected) && Connected
```

It does not check the phase. If `connected == true` can coexist with connecting, reconnecting, disconnecting, or another non-connected phase, this layer can open while the sidecar correctly refuses the same source. Neutral grey sidecar output reduces content exposure, but it does not make the bridge's source predicate correct.

Use exactly the same phase-qualified predicate as the sidecar. The supplied material does not show the JSON schema, so I cannot tell whether `connected` is already phase-qualified or where the phase field resides; if it is already qualified, document that and this finding drops away.

### 3. The literal “never remains bound while closed” guarantee is not provided

During ordinary operation the routing is good, but the MID binding is cached. `IsMonitorFeedAllowed(Now)` becoming false does not itself change the material; something must call `SelectMonitorFrame()`.

In particular, when the 1.5 s confirmation expires merely because time advances:

- normally the character's next tick calls `SetMonitorFeedFrame()` and unbinds;
- without character renewal, the 0.5 s `Poll` timer catches it;
- a game-thread hitch can delay both, while the render thread continues displaying the old binding.

Observing an actual backend privacy/Vagon transition additionally takes poll/network detection time. `ClearPrivateState`, once entered, does unbind immediately and correctly.

If the owner's rule is a literal zero-window material-binding invariant, **this is also blocking by design**. If the accepted rule is “unbind on the next game-thread routing decision, with the sidecar grey cut covering detection latency,” that acceptance window should be stated explicitly.

## What is correct in the privacy/upload path

Within the supplied diff:

- All six former PC-bridge `PCFrame` writes are routed through `ShowFrame()`. I cannot audit unchanged code such as `native_cinematic_pc.inc` for additional writers.
- `ClearPrivateState()` clears the feed state before `ShowFrame(TerminalCanvas)`, so it really does reselect the terminal picture.
- `SetMonitorFeedFrame()` rechecks the bridge gate rather than trusting the character's cached gate.
- A pump launched with stale `Accept=true` cannot by itself publish a frame after a close: the game thread rechecks `Accept`, epoch, quarantine time, and `ConfirmedAt` before upload.
- A generation or gate transition changes the epoch; the next pump drops its old ring/buffer, and old `Ready` frames are rejected.
- The character only requests binding after a successful upload in the current epoch, and the bridge can still refuse it.
- Loss of progress falls back to the bridge picture and blanks the feed texture on the bound-to-unbound transition.
- `display.available` and `display.kind == "graphical"` are both required by `NoteMonitorFeedSource`.

One diagnostic issue: the first fallback log can report reason `"-"` because `StreamerVisualMonitorFeedBound` is updated after the log; `GateReason` also is not refreshed while the gate remains closed but its closed reason changes.

## Threading and lifetime

The main mechanisms look sound:

- `Busy` prevents overlapping `Pump()` calls.
- Only the pump owns the fd, parse buffer, ring, and decoder.
- `Ready.exchange()` gives each decoded frame a single owner in both producer/consumer interleavings.
- Capturing `TSharedPtr<FSub01MonitorFeed>` in the task prevents destruction of the feed while a pump runs. If the character releases its reference first, final destruction can occur on the worker; nothing in the feed destructor requires the game thread.
- The moved pixel allocation and region remain alive until the `UpdateTextureRegions` cleanup. Deleting `Owned` and `Done`, and decrementing the atomic counter there, is the expected ownership pattern.
- The new texture references are properly GC-visible: the character texture, bridge persistent/feed/own/bound textures, and device `PersistentImages` are all `UPROPERTY`.

Two qualifications:

1. **There is no explicit monitor-feed shutdown on the character's `EndPlay`.** Shared ownership prevents a UAF, but it does not guarantee prompt fd closure. If ticking stops before UObject destruction, the fd can remain open and the sidecar can continue to believe a reader exists. Add an owner-lifetime stop operation that requests closure on the task side; do not close the fd directly on the game thread while a pump may own it. This is blocking if level restart/PIE-style lifetime is supported, rather than strictly one character for the whole process.

2. **The upload counter is not a global memory bound.** Only the feed checks it. PC/device uploads can continue accumulating during a render-thread stall. Also, a feed upload starting at count 2 can perform both `Clear()` and `Update()` and reach 4. That is acceptable as approximate feed backpressure, but not as a general stalled-RHI memory guarantee.

## UE API assessment

None of the listed APIs stands out as fictitious:

- `UTexture2D::CreateTransient`, `GetResource()`, `UpdateTextureRegions()`, and `FUpdateTextureRegion2D` are the expected runtime texture APIs.
- `SRGB`, `NeverStream`, `Filter`, `AddressX`, and `AddressY` exist; setting them before `UpdateResource()` in `Ensure()` is the right order.
- The ImageWrapper calls, including `GetRaw(ERGBFormat::BGRA, 8, TArray64<uint8>&)`, are the expected interface.
- `FImageUtils::DecompressImage`, `FImage::CopyTo`, `RawData`, and `NumSlices` are used plausibly.
- The listed post-process fields and `AEM_Manual` exist.
- `TMap<FName,TObjectPtr<UTexture2D>>::FindOrAdd(Device)` does return a `TObjectPtr<UTexture2D>&`, so it matches `Ensure()`.

Behavioral caveats:

- `UpdateTextureRegions()` returns `void`; your `true` means “submitted,” not “copied successfully.” A non-null resource is not a visual verification of the update.
- Do not rely on the cleanup always running on a render thread in every early-out/shutdown path. Your cleanup is thread-agnostic, which is good, but the stub should test rejected/early-out submission and counter recovery.
- This is **not** a UE 5.8 compile verification. Only a real module build can confirm version-specific signatures, includes, and the actual cam2 object's post-process type.

## JPEG walk and pump

I found no blocking out-of-bounds or ownership error in the marker walk.

The following are handled correctly:

- segment lengths, fill bytes, stuffing, restart markers, multiple SOS sections, and EOI;
- an EOI inside a length-delimited segment not terminating the frame;
- split trailing `FF` and `FF D8`;
- retaining an unfinished frame while consuming completed data;
- copying the newest complete JPEG before erasing the parse buffer;
- bad/oversized frames causing SOI resynchronization.

The pump also does the right things for a nonblocking FIFO:

- retries `EINTR`;
- treats `EAGAIN`/`EWOULDBLOCK` as drained;
- keeps the descriptor on `N == 0`, which is appropriate for a FIFO temporarily without a writer;
- closes on other errors;
- caps reads at 8 MiB per pump and decodes at most one queued frame.

Verify that the sidecar really emits within the decoder's **1280×1024** limit and the scanner's **4 MiB JPEG** limit; otherwise every frame simply fails decode and the feed falls back.

## cam2 exposure and your EV arithmetic

The restore logic is basically correct: the copied override flags, values, physical-exposure flag, and blend weight are restored before each mode is applied; mode 0 therefore restores the saved state. Modes 1/2 force weight 1, and the default `min=0, max=-1` disables the optional range override.

One caveat: **mode 1 does not force an automatic metering method**. It restores the copied method. If that method were manual, “auto + bias” would not actually be auto. Either force the intended auto method or document that mode 1 means “copied method + bias.”

Your manual-exposure arithmetic is otherwise correct under the stated conditions:

\[
E_\text{manual}=2^b
\]

when physical camera exposure is disabled, and, using the same normalization as your existing tool,

\[
E_\text{auto}=2^{b-EV100}.
\]

Thus, at the webcam's clamped state `EV100 = -3`, `bias = +1`:

\[
E_\text{webcam}=2^{1-(-3)}=16.
\]

Manual bias `-3` gives:

\[
E=2^{-3}=1/8,\qquad \frac{1/8}{16}=1/128,
\]

so it is **7 stops darker**, as you said. Manual `+4` gives 16 and matches that clamped webcam state; manual `+2` gives 4 and is two stops darker.

Likewise, changing the copied automatic bias from `+1` to `-1` multiplies exposure by \(2^{-2}=1/4\): **two stops darker**, all else equal. At the same `-3` clamp it produces scale 4. It is not a guarantee of a fixed difference from the webcam if the two cameras meter different EV100 states, and fixed manual exposure cannot track the webcam if it leaves that clamp.

So I would **not** block the retained mode-1 default or demand manual `-3`.

## What was applied (install_v22.py, tests, README)

1. **EndPlay leaves the feed bound (blocking)**: new `USub01PCBridge::ReleaseMonitorFeed()`, called first in the bridge's `EndPlay`:
   it clears the feed state, selects the terminal canvas (no texture at all when there is none, an explicit `PCFrame` = null),
   then drops `OwnFrame`/`BoundFrame` so no feed texture stays referenced. Tested on the patched bridge's real methods: bound feed
   -> release -> the stub MID's actual `PCFrame` is the canvas; without a canvas it is null (checks 52-55). A mutant without the
   reselection fails check 53.
2. **Vagon predicate weaker than the sidecar's (blocking)**: `NoteMonitorFeedSource` now also requires `vagon.phase == "connected"`
   (the same field and rule as `scripts/streamer_monitor_feed.py`); a missing phase closes the gate. Tested with phases
   "connecting", "login_required", "dashboard" and none, all with `connected` true (checks 37-39, 35). A mutant without the phase
   check fails check 38.
3. **No literal zero-window unbinding**: accepted as "unbind on the next game-thread routing decision (the character's tick, which
   renews or drops the feed every tick, or the bridge's 0.5 s poll timer), with the sidecar's grey cut covering the detection
   latency"; stated in the README's **Acceptance window** and in the code comment of `SelectMonitorFrame`.
4. **Diagnostics**: the FALLBACK log now sets `StreamerVisualMonitorFeedBound` before building its reason (no more `-`); while the
   gate stays closed its reason is refreshed every 0.5 s and a changed reason is logged (rate-limited like the gate line).
5. **cam2 mode 1 did not force an automatic method**: mode 1 now sets `AutoExposureMethod = AEM_Histogram` (the house volume's
   method), so "auto + bias" is automatic even if the copied settings were manual; mode 0 still restores the copied method.
   Tested with a copied manual method (exposure driver checks 2 and 3/6); a mutant without the override fails check 2.
6. **Upload counter is feed-only backpressure**, and **the sidecar's sizes**: documented in the README (1280x720 mjpeg `-q:v 5`
   is inside 1280x1024 / 4 MiB; a larger `--size` shows as `decode_failed=` and falls back).
7. **Offline limits**: the README lists what the tests cannot establish (UE 5.8 compile, RHI smoke test, ImageWrapper on the
   sidecar's real JPEGs, rendered exposure for auto +1/-1 and manual +4/+2).
8. The EV arithmetic was confirmed; the default (mode 1, bias -1) stays.

## Not applied, with the reason

- **An explicit feed stop at the character's `EndPlay`** (Kimi: blocking only if level restart / PIE lifetime matters). The
  character's `EndPlay` is defined in the cinematic sources, outside the files this installer edits, so there is no anchor to hook
  without touching them; it matters only if the level is restarted while the game runs. The descriptor is owned by the pump task and closes
  when the character is destroyed (the task's shared pointer may finish that on the worker), which a map load's forced purge
  does. Documented in the README's **Lifetime** item; to revisit if a level restart is ever used.
- **A stub test of an early-out/rejected `UpdateTextureRegions` submission**: the stub always runs the cleanup; the helper's own
  early-outs (no resource, bad bounds, short buffer) return before anything is counted, which the AddressSanitizer test covers.
  Whether the engine skips the cleanup on any shutdown path needs the real engine (listed for the RHI smoke test).
