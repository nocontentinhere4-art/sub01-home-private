# The render-time sawtooth: mechanism, measurements and fixes (2026-10-24)

Game m3 (UE 5.8.3 editor build, `-game`, Vulkan SM6, cores 0-5 with `-corelimit=6`), cam2 at 60 fps requested, main
view presented to Xvfb `:99` (1920x1080, `VK_PRESENT_MODE_IMMEDIATE_KHR`, 3 images) and grabbed there by the director.
Kimi consultations: `kimi/sawtooth2-mechanism.md`, `kimi/sawtooth2-recreate.md` (and the earlier `kimi/sawtooth.md`).

## Mechanism (short)

The CPU cost of `vkQueuePresentKHR` on the RHI thread (the NVIDIA driver's X11 presentation path on Xvfb) grows by
~3.3 ms per frame over the life of a swapchain and drops back after ~21.7k presents or whenever the swapchain is
recreated. The present is on the frame's critical path: the render thread waits for the RHI thread at the occlusion
fence (`FSceneRenderer::WaitOcclusionTests` -> `WaitOnRHIThreadFence`), and the game thread waits for the RHI thread
two frames back (`r.GTSyncType 0`). So the frame time follows the present cost: ~18.4 ms (54 fps) after a reset,
~22 ms (45 fps) at the end of a ramp.

## Evidence

1. **Not the GPU.** Insights GPU queues: the scene passes per frame are flat (main SceneRender ~7.8 ms, capture group
   ~6.4 ms; `gpu_ms` 10.6-10.7 flat). nvidia-smi over two ramps: 2377-2396 MHz, P1, 90-99 W of 145 W, no throttle
   reasons; GPU utilisation is LOWER at the end of a ramp (48% vs 57%): the GPU is starved, not slower. No other GPU
   work (Chrome, the K07 voice process, the director's NVENC ffmpeg: SM ~0-5%).
2. **The earlier "per-call growth" table was mis-attributed.** `TimingInsights.ExportTimerStatistics` always adds the
   GPU queues to any `-threads` filter (that is the "leak" into the GameThread/worker exports). EndDrawingViewport
   4.4 -> 6.8 ms, "RenderGraphExecute exclusive", DirectLighting, Radiosity and WorldTick were GPU breadcrumb timers,
   whose spans include GPU idle. On the CPU render thread EndDrawingViewport is 8 us. Window A really lasted 52.0 s
   (2,711 frames, 52.1 fps) and window B 40.3 s (1,815 frames, 45.1 fps); the 4,117 "frames" of B were GPU-queue
   events. Redone with `ExportTimingEvents` (thread name, start/end, depth) and exclusive times per frame.
3. **Where the time goes (per frame, A -> B).** RHI thread `VulkanQueuePresent` 8.2 -> 10.8 ms. Render thread
   19.1 -> 22.2 ms, of which +1.8 ms is `WaitUntilTasksComplete` under `ProcessVisibilityTasks` (2.9 -> 4.75 ms: the
   occlusion-fence wait for the RHI thread) and the rest a broad 5-15% slowdown of many scopes. During that wait the
   workers are mostly idle and the RHI thread is inside the present (1.0 of 3.0 ms in A, 2.7 of 4.8 ms in B). Game
   thread and workers' own work are flat (the game thread waits in `Sync_RenderingThread`).
4. **It is user-space CPU inside the present.** /proc per thread over a ramp, per frame: RHI thread user time
   8.8 -> 12.0 ms, system time flat 2.5 ms, minor faults ~0, voluntary switches flat (51/frame), no cgroup throttling
   (6.4 of 10.2 CPUs used); Xvfb :99 CPU flat per frame (~4.2 ms). Render thread ~13 ms user, roughly flat.
5. **The cycle follows frames, not wall time.** 14 consecutive cycles had 21,662 +- 230 frames while their length
   varied 390-450 s with fps (400 s at 54.9 fps = 21,967 frames; 440 s at 49.5 fps = 21,810). 65,536 / 21,662 = 3.03,
   which fits a 16-bit X11 request sequence wrapping with ~3 requests per present. This is a HYPOTHESIS, not a proven
   driver root cause: a per-swapchain present counter would fit as well, and perf/xtrace (which could show the code
   and the requests) are not available on the pod. The growth (+~3.3 ms over ~21.7k presents, ~150 ns per earlier
   present) looks like a list walked once per present.
6. **Recreating the swapchain resets it, and restarts the clock.** `r.VSync 1` (16:31:21) and `r.VSync 0` (16:35:03)
   each recreate the swapchain (one 80-91 ms frame; UE logs "Creating new VK swapchain" only the first time). The
   16:35:03 flip came mid-ramp: frame 20.1 -> 18.4 ms, fps 49.7 -> 54.3. The next reset did not come on the old
   schedule (~16:38:40) but ~21.5k frames after the recreation (16:42:21-31). FIFO and IMMEDIATE behave the same here.

## What does not fix it (runtime cvars; all reverted)

- `r.NumBufferedOcclusionQueries 2`: the visibility fence wait disappears (`ProcessVisibilityTasks` 7.25 -> 1.52 ms
  per frame) but the frame time is unchanged: the render thread then idles 4.3 ms/frame waiting for the game thread,
  which waits 18.4 ms/frame for the RHI thread's N-2 frame fence.
- `r.GTSyncType -1` on top: the occlusion-fence wait comes back (3.9 ms/frame on the N-2 fence), frame time unchanged.
- Conclusion: whatever the buffering, the RHI thread's present (~9.6 ms per frame and growing) sets the pace; these
  cvars only move the wait. `r.RHICmd*`, `r.GTSyncType 1`, `r.OneFrameThreadLag` do not target this (Kimi).

## Interim mitigation: periodic swapchain recreation

ABBA `recr60` (16:50-17:54 UTC, Kimi-designed, `kimi/sawtooth2-recreate.md`): A = no toggles, B = `r.VSync` flipped
every 60 s (`toggler.py`, single alternating flip), legs 15 min + 60 s settle, cam2_fps 60, the same samplers in every
leg (per-thread CPU and run-queue wait, cgroup throttling, nvidia-smi every second). Medians of the game's 10 s PERF
windows:

| leg | arm | frame ms p50 | p95 | fps | render ms | low-fps window (p5) | windows with a >50 ms frame | ramp amplitude |
|---|---|---|---|---|---|---|---|---|
| 0 | A | 20.45 | 22.24 | 48.9 | 17.16 | 45.0 | 7 (stalls up to 818 ms, no toggles) | 1.6-2.7 ms |
| 1 | B | 18.47 | 20.45 | 54.2 | 15.27 | 48.9 | 17 (15 toggles) | 0.15 ms |
| 2 | B | 18.49 | 18.80 | 54.1 | 15.28 | 53.2 | 15 (15 toggles) | 0.11 ms |
| 3 | A | 20.09 | 22.18 | 49.8 | 16.82 | 45.1 | 2 | 3.4 ms |

- B - A = -1.79 ms per frame (paired -1.98 and -1.60; A legs differ by 0.36 ms, B legs by 0.02 ms): +4.3 fps on the
  median, p95 -1.8 to -3.4 ms, the worst 10 s window 45 -> 49-53 fps. The ramp slope inside a ramp is unchanged
  (0.52-0.60 ms/min) and the amplitude is capped (0.1-0.2 ms instead of 1.6-3.4 ms).
- Price: one 74-86 ms frame per flip (a visible freeze of ~4 frames in the stream once a minute). The other long
  frames are unrelated stalls present in both arms (A: 189, 663, 818, 179 ms; B: 168, 176 ms; not aligned with a flip).
- Verdict: under Kimi's preregistered gate (median >= 1.0 ms better and beyond the A-leg spread, p95 not worse,
  hitches toggle-aligned and < 120 ms) it passes descriptively. Under the project's own rule ("a per-leg median delta
  of 2 ms or less is inconclusive") both paired gains (1.98, 1.60 ms) are inconclusive; two legs per arm that do not
  overlap do not override that rule. Either way the base present cost stays, so this does not reach 60 fps.
- EXPERIMENTAL, not left running: Kimi asks for an 8-24 h soak (game and Xvfb RSS, GPU memory, FDs, hitch growth)
  before relying on it, and 120 s rather than 60 s for streaming. `scripts/streamer_swapchain_refresh.py` is the
  hardened version of the test toggler (uid 1001 only, one instance via a lock file, finite period >= 30 s, default
  120 s, stop file as the kill switch, no burst after a suspend, r.VSync 0 written on every normal exit with retries;
  a SIGKILL cannot restore it, so whoever kills it sends `r.VSync 0`). It must be the only writer of the live-console
  file while it runs.

## The ceiling without the X11 present (offscreen ablation)

Game m3o = m3 + `-RenderOffScreen` (same v21 binaries, cam2_fps 60, cores 0-5; launcher
`/root/.sub01-windows-recovery/launch-streamer-game-20261024m3o.py`, 17:54-18:20 UTC). UE then uses the null platform
application and SDL's dummy video driver: no X window, no swapchain, no `vkQueuePresentKHR`. The director kept running
and grabbed a black `:99` meanwhile.

| case | fps | frame ms | render ms | RHI ms | GPU ms | cam2 capture / written fps | sawtooth |
|---|---|---|---|---|---|---|---|
| m3, Xvfb present, capped 60 (ABBA A legs) | 48.9-49.8 | 20.1-20.5 | 16.8-17.2 | 3.84 | 10.67 | ~50 / 40 | 1.6-3.4 ms |
| m3o offscreen, capped 60 (15 min) | 59.8-59.9 | 16.7 | 13.4-13.8 | 4.3-4.4 | 10.3-10.6 | 59.8 / 51.5-53.2 | none |
| m3o offscreen, uncapped (4 min) | 77.2-77.9 | 12.9 | 12.2 | 3.85 | 9.75 | 60.0 / 52-53 | none |

This strongly supports the diagnosis, with limits: offscreen changes the whole platform and presentation path (null
platform application, no swapchain), not only the present, and 15 min capped plus 4 min uncapped do not isolate the
present's cost exactly. As an estimate, m3 frames take 18.4 ms right after a reset and ~22 ms at the end of a ramp,
against 12.9 ms offscreen uncapped, so the X11 present path costs ~5.5-9 ms per frame on the critical path. The 77.5 fps
ceiling is BEFORE any main-view tap: neither the main view delivered to the director at 60 nor a 60/60 margin is
demonstrated yet. cam2 captures 59.8 but writes 52-53: the loss is downstream of the capture (encode, writer or FIFO
back-pressure; not yet located).

## Structural fix (native code + director; for the coordinator, not implemented here)

Goal: no X11 present at all. The game renders offscreen and hands its main view to the director the way it already
hands cam2.

1. **Launch** with `-RenderOffScreen` (a launcher variant like m3o; nothing else changes). No X window, no swapchain,
   no Xvfb copy; Xvfb `:99` and the director's x11grab of it become idle.
2. **Game: main-view tap.** Go/no-go first: on the render thread, subscribe to `FSlateApplication::Get().GetRenderer()->
   OnBackBufferReadyToPresent()` (in 5.8.3 the delegate passes `(SWindow&, ISlateViewportProvider&)`; take the back
   buffer the way PixelStreaming2's capturer in this engine does) and prove, before building the rest, that under
   `-RenderOffScreen` on Linux/Vulkan it fires every frame with non-black 1920x1080 content, a known pixel format,
   a texture that stays valid until the copy is enqueued, and render-thread-only access. If it does not, the tap is a
   different hook (for example the game viewport's render target at the end of the frame). Then per frame:
   `FRHIGPUTextureReadback::EnqueueCopy` into a 3-slot ring (the cam2 pump pattern: never wait for the GPU, drop when
   all slots are busy), lock a ready slot, JPEG-encode 1920x1080 off the render thread, write to `streamer/main.mjpeg`
   (a FIFO created by the game) with `streamer/main.json` (fps, last frame time, drops, sequence) like `cam2.json`.
   Budget: 8.29 MB per frame GPU->host (0.5 GB/s at 60); a 1080p JPEG is ~2.25x cam2's 720p one (~3.2 ms per call
   today on a background worker), so ~7.2 ms of one core per frame (~0.43 core at 60 fps), plus the director's 1080p
   MJPEG decode; measure p99 encode time under full pod load and keep enough encodes in flight (ordered output) for
   60. Transport: a JPEG frame is far larger than PIPE_BUF, so FIFO writes are not atomic: define framing and
   behaviour on a full pipe (whole-frame drop decided before writing, or a blocking writer thread with a bounded
   queue), on a missing reader (EPIPE/SIGPIPE ignored, reopen) and on a reconnect (the reader resyncs on SOI), or use
   another transport (shared-memory ring). cam2 captures 59.8 but writes 52-53 of 60: find that loss first, the main
   tap shares the design.
3. **Director.** The input mode is explicit, never inferred from a missing file: `--game-source fifo` (offscreen
   game) or `--game-source x11` (windowed game, today's x11grab of the `:99` window). In fifo mode input 0 is
   `-thread_queue_size 512 -use_wallclock_as_timestamps 1 -probesize 2000000 -analyzeduration 1000000 -f mjpeg
   -framerate 60 -i <streamer-dir>/main.mjpeg`, scaled like cam2 (`cam2_scale`: full-range MJPEG to limited range),
   `tpad` clone after EOF, and a staleness check like cam2's (`main.json` older than N s or no writer: a visible
   placeholder, never a silent black `:99` grab, and back when it recovers). The FIFO has one reader (the director's
   ffmpeg); anything else that wants the picture takes it from the director (preview/tee), never from the FIFO.
4. **Operator view.** With `-RenderOffScreen` there is no window at all (UE uses the null platform application), so
   there is nothing to hide or minimise; the operator watches the director's preview/local HLS. A
   windowed-but-minimised game is not a substitute: the present path stays (or turns into out-of-date swapchain
   recreations), unverified and not recommended.
5. **Expected result and acceptance.** The ablation ceiling is 77.5 fps uncapped before the tap; the tap adds the copy
   and ~0.43 core of JPEG, so 60/60 is plausible but not shown. Accept with a four-leg ABBA, tap off vs on, against
   m3o with the real director, then an >= 8 h soak. Suggested gates (Kimi): >= 59.5 unique main-view fps arriving at
   the director's ffmpeg, <= 0.5% drops, p95 frame-time regression <= 0.5 ms, no tap-aligned > 50 ms frames, no
   sawtooth, CPU/RSS/FD/GPU memory stable and within the 6-core budget; cam2's 52-53 fixed or explicitly waived.
   Fault tests: kill and restart the game and the director, suspend/resume; frames stay whole and ordered, the
   placeholder appears and recovery is bounded, the windowed fallback still works, never black output.
6. **Until then (experimental, pending a soak):** `scripts/streamer_swapchain_refresh.py` caps the sawtooth at
   ~0.2 ms and holds ~54 fps instead of 45-55, with one ~80 ms frame per flip; the runtime cvars tried here do not
   help.

## Tools (`tools/sawtooth/`, run on the pod from `/tmp/sub01-share/w-sawtooth/`)

- Insights exports: use `TimingInsights.ExportTimingEvents FILE -columns=ThreadName,TimerName,StartTime,EndTime,Depth
  -threads=... -startTime=... -endTime=...` (not `ExportTimerStatistics`, which always mixes in the GPU queues).
  `excl.py` (exclusive/inclusive time per frame per thread and timer), `excmp.py` (compare two windows), `parents.py`
  (where a timer is called from), `during.py` (what the other threads run while one thread is inside a timer),
  `evframe.py` (an indented timeline of a few frames).
- `cycles.py`: sawtooth cycles from the game log (duration and frame count per cycle).
- Legs: `legsample.py` (per-thread CPU and run-queue wait, cgroup throttling, RSS), `rhisample.py` (user/system time,
  faults and context switches per thread), `abba2.py` (long-leg ABBA with the MEASURING lease; arms are live-console
  commands or `toggler:PERIOD`), `abbasum.py`, `ramps.py` (slope and amplitude per ramp), `hitches.py` (long frames and
  whether a flip caused them), `toggler.py` (the test flipper used in `recr60`).
