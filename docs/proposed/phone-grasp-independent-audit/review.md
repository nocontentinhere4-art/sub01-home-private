# Independent phone grasp source review

This is a read-only review of the pinned sources in `audit-scope.json`. No R5 skin vertices were recomputed, no solver/render/native activity ran, and no new motion variant was created. The existing measured R5 remains rejected: pad error 0.0001078 mm, 9,098 case-interior vertices, maximum 7.49905 mm depth, 2,130 left-front violations. R3 already has strict triangle crossings (case223L/293R, screen152L). Those are existing reports, not new measurements from this audit.

## Coordinates and inverse binds

No concrete centimetre/metre conversion defect was found. In `device_motion_phone_bootstrap.mjs:41–42`, `phoneWorld` is explicitly composed with uniform scale0.01 and the mount is `inverse(W_RightHand) * phoneWorld`. Consequently the matrix to validate is **the complete `W_RightHand * mount`**, whose linear basis must be orthogonal with scale0.01 metres/canonical centimetre and positive determinant. The raw mount itself need not have scale0.01: an owner hierarchy already scaled0.01 can produce a mount with scale1. Checking raw mount scale alone would produce a false unit diagnosis.

The canonical source transform is `100*[delta.x,-delta.z,delta.y]` about the actual source case132 AABB centre (`review_blender.py:100–124`). This is a proper axis rotation followed by metre-to-centimetre conversion. The refine code's half sizes `[rawXspan,rawZspan,rawYspan]*50` (`refine_contact.py:73`) are the matching half extents in centimetres. Multiplication by10 for residual millimetres is consistent. A world-space skin error must be multiplied by1000 if reported in millimetres; it must not receive the canonical-centimetre conversion a second time.

The compose evaluator (`compose.mjs:35–53`), refine evaluator (`refine_contact.py:57–70`) and direct review evaluator (`review_blender.py:81–87`) all use the correct glTF world-skin expression `sum(weight * JointWorld * IBM * POSITION)`. The mesh node's current world matrix cancels in the world result; adding it again would introduce a real basis error. Refine/readback enumerate every JOINTS_n/WEIGHTS_n set and check weight sum. Bootstrap currently enumerates only sets0/1 and normalizes its witness by its accumulated sum (`bootstrap.mjs:17–20`); this is harmless only while the actual source has at most8 influences and sums agree. Assert that precondition before using its witness with the non-renormalizing evaluator. Do not alter the validated R9 mesh, rest, IBMs or weights to fit the prop.

The source screen-front sign still needs an explicit check: bootstrap points the chosen palm normal towards the head, but does not assert that the actual source screen136 lies on positive canonical Z. Derive that sign from actual screen geometry/normals, not from an assumed palm orientation. This is a missing invariant, not evidence that R5 actually has a flipped screen.

## Why the tiny pad error does not prove a grip

1. **The witness is not an identified volar pad.** `bootstrap.mjs:20,45` selects an index3-dominant surface vertex nearest Index4. This may be a nail-side, tip or lateral surface point. No normal or contact patch is checked. `compose.mjs` aligns the Index1→Index4 chain axis to the screen approach axis; a finger long axis is not its volar surface normal. One surface point can match a screen point while its phalanx or palm passes through the case.
2. **The whole surface is absent from the objective.** `refine_contact.py:75` selects at most300 index-spaced vertices plus150 vertices deep in the case in the INITIAL pose, then holds that selection fixed. Newly penetrating vertices brought into the case by a correction are not necessarily penalized. Full diagnostics run only after optimization. This directly permits a low sampled cost with thousands of final penetrations.
3. **Part of a bad grip can be unreachable by the allowed variables.** `refine_contact.py:45` changes LeftArm/ForeArm/Hand/index and15 right finger rotations; it does not change RightArm, RightForeArm, RightHand or the wrist-to-phone mount (`:71`). Right-palm vertices influenced only by fixed joints are invariant. If any such vertex is in the case, no right-finger30° correction can remove it. Actual invariant-collision counts must be measured; this review does not assume which of the9,098 vertices are invariant.
4. **Right-hand targets are newly invented end-point goals.** `refine_contact.py:79–88` chooses one distal vertex per digit and clamps it to opposing case faces/near edges. These targets do not establish a captured palm fit, pad normals, phalange clearance or a feasible grasp. The initial mount was also a source-palm extreme plus2 mm clearance, shifted2 cm and rotated in-plane90° (`bootstrap.mjs:28–42`), not a measured original phone-to-palm transform.
5. **Hard projection gives one point priority over the grip.** `refine_contact.py:109–119` projects only the left witness using9 arm/wrist variables. The least-squares cost then gives that point500× residual scaling, while case penetration is a soft sampled penalty (`:91–98`). Step acceptance tests cost and pad projection, not full-hand nonpenetration. A point can remain essentially exact while the hand rolls around it into the device.
6. **Behind the screen is not automatically inside the phone.** The `front` term (`refine_contact.py:95–96`) penalizes every left sample within the screen XY rectangle that is behind its plane, even if it is behind the back case and outside the solid. The review code already labels this distinction (`review_blender.py:137–145`). An unsigned OBB interior/plane penalty is useful broadphase evidence, not a complete signed solid constraint or penetration depth proof for a rounded multi-part device.
7. **A single2 s solution is baked across a moving clip.** The optimization is evaluated at2 s, then the same local right-finger deltas are applied over the whole4 s and left deltas are faded over1–3 s (`refine_contact.py:145–156`). A feasible2 s pose would still not establish contact, collision freedom, or smooth grip throughout playback.

## One corrective plan

Freeze the accepted R9 geometry/rest/IBMs/weights and stop blind rigid-mount sweeps. Before solving, independently compare full all-influence posed vertices against the direct Blender readback at several captured times; validate the complete phone-world0.01 basis, the case-centre canonical frame and the actual screen normal sign.

Start with a captured support-grasp phase and measure the complete palm, thumb web and every phalange against the actual case/screen mesh. Explicitly count colliding vertices whose weights are entirely on fixed joints. If those exist, declare the present finger-only problem infeasible and revise the *articulation* of the captured support arm/wrist or use a provenance-reviewed mount fit; do not touch mesh, binds, bone lengths or silently increase angle limits. A rigid prop cannot fix an incompatible fixed palm by moving fingertips alone.

Identify a genuine volar index contact patch from source anatomy and posed triangle normals, with multiple non-collinear surface witnesses and the pad normal opposing the actual screen outward normal. Use these patch constraints rather than endpoint distance or finger-axis alignment. Include whole-palm/phalange surfaces in a dynamically refreshed collision active set. Use the OBB only to nominate nearby geometry, then enforce actual surface/solid nonpenetration and hand self-contact before accepting a contact refinement; the pad hard projection must not buy an increase in full-hand collisions.

Preserve the captured timing and articulate a bounded feasible interval. Recheck actual all-influence surface triangles at its knots and between them, including the support hand, thumb web, active finger, palm and cuffs. Retain source-only/unaccepted flags until this full geometry check and a direct close visual review pass. Do not render or import another candidate merely because one pad distance is tiny. Any new heavy attempt needs the separately authorized remaining source-compute budget; this review does not extend it.
